# Listing modals

My Listings opens Add/Edit using `mountListingForm`, View using `mountListingDetails`, and a permanent-deletion confirmation. Admin listing management reuses these dialogs. Browse cards navigate to `/listings/:id`; the public details page uses the same details component. All database operations remain in existing services and RLS remains the authorization boundary. My Listings still queries only owned rows; Edit checks the retrieved owner or administrator role, and form payloads never include owner IDs. The services emit one success/error outcome per mutation; modal hosts add no duplicate notification.

`createListingModals()` owns one body-mounted host with three Bootstrap modal instances (Add/Edit share one dialog). Only one opens at a time. Bootstrap handles Escape, backdrop dismissal, and focus trapping; boundary Tab/Shift+Tab wrapping keeps focus in the dialog. On close, focus returns to the opener or a stable page fallback after table refresh. Modals use synchronous transitions so navigation can fully dispose instances/backdrops before mounting the next page.

Add/Edit Cancel, close button, Escape, and backdrop dismissal all use the shared dirty-form guard. Closing is blocked while saving; saves are submitted once and failed saves retain fields. Router links/history and native unload retain existing unsaved-change protection. Successful saves mark the form clean, close it, and refresh the owned table. A refresh requested during a table load is queued. Deletion disables its controls while pending, retains the dialog on error, and refreshes after success.

Hidden dialogs unmount their form/details content. Page cleanup aborts event handlers, releases guards, hides/disposes Bootstrap instances, and removes the host. Late details/form/table responses cannot render into another listing or page. Shared details include product fields, attachments, seller name/email, a favorite control and owner actions. They use safe text and image URL handling, preserve plain-text line breaks, and have loading/missing/error/retry states. No rich-text library is used.

The `/listings`, `/my-listings`, `/listings/add`, `/listings/:id/edit`, and `/listings/:id` pages remain available. Action links retain their hrefs for modified clicks/new tabs; ordinary clicks on My Listings use modals. Direct Add/Edit routes still use the shared form, while Details uses the same read-only component as View.

## Verification

Start Vite and run `node scripts/verify-listing-modals.mjs` using the optional independent Playwright tool described in the root README. Set `PLAYWRIGHT_MODULE_PATH`, optionally `CHROME_PATH`, and `LISTING_MODALS_TEST_URL` (default `http://127.0.0.1:5180`). The Node process reads ignored `.env.seed.local` only to create and remove marked temporary fixture accounts in the confirmed project; the browser receives only public configuration. No existing demo account is overwritten. The existing Sofia admin account is used only to edit a temporary listing.

Checks cover public View and direct details/refresh, loading/missing/error/retry, safe plain text, stale responses, focus/Tab/Escape, modal create/edit/delete, inline validation, cancellation/dirty warnings, duplicate submissions, failure recovery, toasts, owned-table refresh, owner spoof rejection, real non-owner RLS denial, admin ownership preservation, mobile layouts, and history/navigation cleanup. Temporary accounts and related rows are removed in `finally`. `scripts/verify-listing-crud.mjs` separately exercises retained page CRUD and guards. Public Home/Browse regressions, service/auth/dirty-guard tests, and the production build should also pass.
